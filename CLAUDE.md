# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**SiEBERT MLX** (`siebert-mlx`) is a Streamlit application for sentiment classification in English text using SiEBERT (`siebert/sentiment-roberta-large-english`) on Apple Silicon with MLX. Users upload a CSV (or try the built-in sample data), select the text column, classify, and download results with added "Sentiment" and "Confidence" columns — renamed to "Sentiment (model)" / "Confidence (model)" when the CSV already uses those names, so source data is never overwritten. Wide layout with the inputs in the sidebar (uploader, Sample, then the text-column picker and Classify/Reset once a file is loaded) and the main area left to the data: a Get started card on the landing page, a whole-file preview before classifying, then a summary band — metric cards (including a `Skipped` card when the file has blank text cells) beside the distribution chart — over the results table, which pins the prediction and its confidence to its left edge and carries Download in its header. Text columns are auto-detected, and a Reset button — available from every state a loaded file can reach — starts over. The `Sample` button carries a `help=` tooltip: its label alone does not say what it loads, and the Get started card, the only other place that names it, is gone once a file is loaded.

## Architecture

Single-file application (`streamlit_app.py`):

1. **`detect_text_column`** — returns first string- or object-dtype column name via `next()` generator. The dtype predicate itself lives in **`_is_text_dtype`** (`pd.api.types.is_string_dtype` / `is_object_dtype`, matching the pandas 3.0 default `str` dtype), the one definition of "what counts as a text column" — `detect_text_column` is its only caller since the width cap dropped its dtype clause (see the column-widths bullet), so it is no longer shared with `_render_results`
2. **`_ensure_safetensors`** — downloads model via `snapshot_download` (`allow_patterns` is a union, not a preference order: it fetches whichever of `model.safetensors`/`pytorch_model.bin`/`config.json` `main` has — today the `.bin` and `config.json`; the safetensors preference lives in the `exists()` guard, which skips the conversion, not the download), converts to safetensors if needed; `torch` and `safetensors` are lazy-imported only when conversion is required. The conversion writes to a sibling `model.safetensors.*.tmp` and `os.replace`s it into place — the `exists()` guard means a truncated destination would be accepted forever, so the write has to be all-or-nothing; the `finally` unlink covers every failure path and is a no-op once `replace` has consumed the temp file. **The mode is reapplied after `save_file`.** safetensors 0.8.0 writes through its own temp file and renames it over the destination, so its output is 0600 whatever the umask (0.6.2 and 0.7.0 left 0644) — and the `mkstemp` this used to create the temp file with was a second, independent 0600. Either way `os.replace` carried an owner-only checkpoint into a Hugging Face cache that may be shared. The temp file is now created by hand, `os.open(..., O_CREAT | O_EXCL, 0o666)` under a `uuid4` name, which is a plain create, so the kernel applies the umask; its mode is read back and `chmod`ed onto the file once `save_file` has replaced it. Read back rather than via `os.umask()`, because setting the umask to read it changes it for every thread in the process — the same probe `huggingface_hub` uses for its own blobs. `test_converted_file_honors_the_umask` pins it with a `save_file` double that **replaces** the file the way 0.8.0 does; the bare module-level mock never touches the file and so cannot tell a converter that reapplies the mode from one that does not. Its two umasks each rule out a different wrong fix (all three mutation-tested): `0o022` fails without the `chmod` and with a 0600 create, and `0o077` fails with a hardcoded `0o644`, which would widen a deliberately strict umask
3. **`load_model`** — loads config via `AutoConfig`, constructs `RobertaForSequenceClassification`, loads weights via `from_pretrained` with `float16=True` (weight **memory** only — since mlx-transformers 0.3.0, `get_extended_attention_mask` hardcodes a `mx.float32` additive mask, which promotes every encoder activation, so `.logits` come back `float32` and compute is fp32 regardless; there is no input-side lever, `roberta.py` never passes `dtype`), then `mx.eval(model.parameters())` to materialize the lazy weights on the loading thread; cached with `@st.cache_resource(show_spinner="Loading model...", show_time=True)`; authenticates with `HF_TOKEN`. The spinner text lives **on the decorator, not in a `with st.spinner(...)` around the call**: `show_spinner` defaults to `True`, so wrapping the call stacked two spinners on a cache miss — the app's plus Streamlit's own ``Running `load_model()`.``, which leaks an internal symbol onto the one screen that is otherwise empty. `show_time=True` because a cold cache is a ~1.4 GB download plus the safetensors conversion, and a static spinner for minutes is indistinguishable from a hang. The **call site** is below the page chrome (see the UI bullet), not next to this definition
4. **`process_dataframe`** — pre-filters blanks, **sorts the surviving rows by text length**, batches them (`BATCH_SIZE=8`), tokenizes with `return_tensors="np"` and converts to `mx.array`, calls the model with `return_dict=True` (see the `set_verbosity_error` bullet in Key Patterns), classifies via softmax over logits; uses `.tolist()` for batch conversion; clears its `st.progress` bar (`progress_bar.empty()`) when done. The sort (`valid.sort(key=lambda pair: len(pair[1]))`) is a padding optimization, not a semantic one: each batch is tokenized with `padding=True`, i.e. padded to the longest sequence *in that batch*, so in file order one long review drags the other seven rows through all 24 encoder layers at its width — attention being quadratic in that width. Sorting confines long rows to their own batches. Character length is a free proxy for token length. **Row order in the returned frame is untouched** — `indices` still carries the original positions and the write-back is by `idx`, never by batch position (`test_batching_preserves_original_row_order`). Returns a **2-tuple**, `(result, GeneratedColumns(sentiment, confidence))`, not a bare frame: the two appended column names are conditional on the input, so the function that writes them is also the one that reports them (see the collision bullets in Key Patterns)
5. **UI** — `layout="wide"`, with the inputs in `st.sidebar` and the output in the main area (see the layout bullets in Key Patterns). Sidebar, top to bottom in the order the steps are taken: file uploader → `Sample` → a reserved `sidebar_controls` container (text-column selectbox + Classify/Reset once a usable file is loaded, Reset alone for an unusable one) → model-link caption. Main: title + orienting `st.caption`, then one arm of the foot-of-script state chain — Get started card / `st.error` / `st.warning` / the whole-file preview (which the results table replaces, see the preview bullet) / a summary band (metric cards + sentiment-distribution chart) over the Results card (source name and Download in its header row). Results are stored in `st.session_state` and re-rendered from there, so post-classify reruns don't re-run inference. **`load_model()` is called below the chrome** — after the whole `with st.sidebar:` block (uploader, Sample, the reserved controls slot, model caption) and the title/caption, before the upload handler — not at the top of the script. Nothing above the classify branch needs the model, but Streamlit emits deltas as the script runs, so loading first meant the page body was *nothing but* a spinner until the weights were ready: no title, no uploader, nothing to click. That is minutes on a cold cache and still the fp16 load plus `mx.eval` on every fresh process, and it is not one-session-only — `st.cache_resource` holds a compute lock (`cache_utils.py`: "only one of those sessions computes the value, and the others block"), so every session connecting during the first load gets the same empty page. Kept **eager** rather than moved into the classify branch so the load still overlaps with the user choosing a file (the uploader posts to `/_stcore/upload_file`, which does not wait on the script thread), and so `streamlit_app` still calls `load_model()` at import — which is what `tests/conftest.py`'s module-level patches exist to intercept

## Key Patterns

- MLX for all inference on Apple Silicon (no device management needed)
- MLX streams are thread-local; Streamlit runs each rerun on a fresh thread, so `load_model` must `mx.eval(model.parameters())` to materialize the weights before caching. Skipping this leaves the float16 weights as pending ops bound to the loader thread's streams, and the first classify (a later rerun thread) fails with `RuntimeError: There is no Stream(cpu, 1) in current thread.` — the text since mlx 0.32.0; 0.31.2 reported `Stream(gpu, 0)` for the same bug, so grep for both. Re-verified 2026-09-23 on mlx 0.32.2 (load on one thread, forward on another): still required
- `hf_logging.set_verbosity_error()` raises the level of transformers' own `transformers` logger only, not huggingface_hub's or mlx-transformers' (which logs to its own stdlib logger, at INFO). There are no checkpoint warnings left for it to catch: weights load through mlx-transformers, not transformers' `from_pretrained`. In the current stack it hides **nothing**, and is kept as a guard against future transformers log noise. The one thing it was hiding until 2026-09-23 was the `use_return_dict` deprecation, logged on the first classify because mlx-transformers 0.3.0 falls back to `config.use_return_dict` whenever `return_dict` is `None`. That read is in `RobertaForSequenceClassification.__call__`, which passes the resolved value on to `RobertaModel`, so the identical fallback there never runs on this path (and `RobertaEncoder` never reads the config at all)
- **The forward call passes `return_dict=True`** (`model(**inputs, return_dict=True)`) for that reason. transformers is actively removing deprecations (5.17.0's notes list several, e.g. #48367 "Deprecated stuff gone"), and removing that property would be an `AttributeError` on the first real classify — which the mocked suite cannot see and which `set_verbosity_error` would never have surfaced beforehand. Passing it explicitly skips that read, and the logits are identical (the integration suite's pinned confidences are unchanged). Verified with a negative control: a transformers-logger handler at WARNING records the deprecation for a bare `model(**inputs)` and nothing for a full `process_dataframe` run. `test_forward_passes_return_dict_explicitly` pins the argument on every batch (mutation-tested)
- Confidence via `mx.softmax(logits, axis=-1)` with `mx.max` and `mx.argmax`; `mx.eval()` before `.tolist()`; labels from `model.config.id2label`
- Empty, whitespace-only, and missing (`NaN`) texts skipped; get sentiment `""` and confidence `0.0` (`fillna("")` before `astype(str)` coerces pandas 3.0 missing cells, which no longer stringify to `"nan"`)
- Tokenizer uses `return_tensors="np"` converted to `mx.array`, with `truncation=True` (512 token limit) and `padding=True`
- `process_dataframe` returns a copy; input DataFrame is not mutated
- `st.session_state` persists the loaded DataFrame (`df`/`source_name`) and the classification result (`result_df`/`result_col`/`result_generated_cols`) across reruns, so a post-classify rerun (a manual Rerun, the file watcher after an edit, a widget change that keeps the column) re-renders from state instead of re-running inference; the result is invalidated when the selected column no longer matches `result_col`. The three `result_*` keys are written in one branch and popped together by `_clear_results` — `result_generated_cols` names columns *inside* `result_df`, so a survivor would be applied to the next file's results. Do not confuse it with `result_col`, which is the **input** text column. They can still come apart across a **code** change, which is why `"result_generated_cols" in st.session_state` is part of the render guard rather than assumed: streamlit's file watcher reruns an edited script against the session_state already in memory, so a session holding results from before that key existed hit an uncaught `KeyError` and rendered a traceback in place of the page. The guard degrades it to the pre-classify view; the lookup inside stays an index, not a `.get()` default, because a default of the plain names would tint, size and count the user's own `Sentiment` column on exactly the input the indirection exists for. `test_results_missing_the_generated_pair_degrade_instead_of_crashing` pins it
- `Sample`/`Reset` are `on_click` callbacks (mutate `session_state` before the rerun, no `st.rerun()`); `Classify` still uses the `st.button`-returns-`True`-only-once-after-click pattern (`classify_clicked`)
- Uploaded files load once, guarded on `uploaded_file.file_id`, and the uploader has a dynamic `key=f"uploader_{...}"` that `Reset` increments — without both, the persisted uploader value re-reads on every rerun, undoing `Reset` and clobbering a `Sample` pick
- **The has-file → no-file transition has its own arm.** `elif uploaded_file is None and "_uploaded_id" in st.session_state:` pops `_uploaded_id`, `df`/`source_name` and the results. Clicking the uploader's **X** makes `st.file_uploader` return `None`, which fails the `file_id` guard above, so the whole branch was skipped and `df` was read straight back out of `session_state` — leaving the preview, metrics, chart, results table and a Download button all describing a file the uploader now reported as absent. Same rule the failed-read arm already enforces, applied to the one transition nothing else observed. **Guarded on `_uploaded_id`, not a bare `is None`**: the uploader is empty by construction on the rerun that `_load_sample` populates `df`, and both `_load_sample` and `_reset` pop `_uploaded_id` via `_reset_uploader`, so neither path can reach here and wipe the data it just loaded — widening it to a bare `is None` fails `test_sample_button_populates_session_state`, `test_stale_upload_does_not_override_sample` and `test_sample_survives_the_empty_uploader_it_is_loaded_alongside`. Popping the id rather than calling `_reset_uploader()` is deliberate too: bumping `uploader_key` would remount an already-empty widget. `test_removing_the_uploaded_file_clears_data_and_results` pins the arm itself
- **The text-column selectbox is keyed to the loaded dataset**, `key=f"text_column_{uploader_key}_{_uploaded_id or 'sample'}"`. Unkeyed, its widget identity is a hash of `(label, options, index, help, ...)` (`elements/widgets/selectbox.py` → `compute_and_register_element_id`), so two files with the same header list **and** the same auto-detected column shared one widget: a manual override on the first was silently reapplied to the second, and `index` — the auto-detect — was ignored. That rule was an implementation detail of Streamlit's id computation rather than anything this app chose. Keying on the load makes it explicit: every new upload, `Sample` or `Reset` mints a fresh widget, so auto-detect applies to every file. Both inputs are available by then — `uploader_key` from the `setdefault` near the title, `_uploaded_id` written before this branch renders. `test_auto_detect_reapplies_to_a_file_with_the_same_headers` pins it
- A failed `pd.read_csv` (**`except ValueError`**, and the `try` holds exactly one statement: `ParserError`, `EmptyDataError` and `UnicodeDecodeError` all subclass `ValueError`, so the four-name tuple this used to list — and this bullet used to advertise — was *exactly* `except ValueError` while reading as a curated allowlist of parse failures. Narrowing the block to the read is what keeps that equivalence harmless; a second statement there would have its own `ValueError`s swallowed and shown as a malformed CSV with the real cause discarded) pops `df`/`source_name` and the results before the `st.error` renders — a rejected upload must not leave the previous file's preview and results on screen as if they were its own. The `except` arm itself renders nothing: it calls `_clear_data()` and sets `read_failed = True`, and the error renders in the first arm of the foot-of-script state chain (see the failed-read Reset bullet). `_uploaded_id` is advanced **only** in the `else` arm: leaving it stale is what re-renders the error on the next benign rerun instead of letting it vanish, and `test_malformed_upload_shows_error_and_clears_data` / `test_upload_error_persists_across_reruns` pin both halves
- Walrus operator (`:=`) in UI guards to combine detect + check into one `elif`
- `SAMPLE_DATA_PATH` points to `samples/mixed_sample.csv` for the "Sample" button
- **Layout — wide, with the inputs in the sidebar.** `st.set_page_config(layout="wide")`, with `initial_sidebar_state` left at the default `"auto"` (expanded on desktop, collapsed at 768px and below). `"expanded"` was tried first and differs only on those narrow viewports, where the sidebar overlays the main area instead of pushing it aside — so it opened a phone on an overlay covering the Get started card, the one element written for a collapsed sidebar. Either way, below 768px the sidebar stays open over the results of whatever was just clicked in it until the user closes it (Streamlit does not close it on widget interaction); that is the cost of a sidebar layout on a phone, documented rather than engineered around. `with st.sidebar:` holds the inputs top to bottom in the order they are used: uploader, `Sample`, a reserved `sidebar_controls = st.container()`, then a model-link `st.caption`. The reserved container is filled at the foot of the script — the Text column selectbox + Classify/Reset in a horizontal container, or Reset alone — because what goes in it depends on the loaded file, which is settled only after `load_model()` and the upload handler have run; reserving it keeps those controls under the uploader and above the model note, while the note still renders before the load blocks. The foot of the script is **one if/elif chain over file state** — `read_failed` / `df is None` / `df.empty` / no text column / `else` — so each arm owns both halves of its UI: its message in the main area and its controls in the sidebar via `with sidebar_controls:`. The classify branch stays in the main-area flow, so its spinner and progress bar render in the main area under the caption, not beside the button that started them. `_download_button(result_df, source_name)` is the one Download, kwargs unchanged (lazy `data=`, `on_click="ignore"`, `key="download"`), called from both arms of `_render_results`' all-blank split — standalone in the all-blank arm, in the **Results** header row otherwise; one `key` is safe because the arms are exclusive. `layout="wide"` was once rejected as the fix for a 58px grid overflow (see README Screenshots); it was adopted for this layout, and it does **not** retire `TEXT_COL_WIDTH` (see the geometry bullet). **Where things render is pinned separately from whether they render**, because every other lookup (`at.button(key=...)`, `at.dataframe`, `at.error`) searches the whole tree and stays green wherever a widget lands: `test_inputs_live_in_the_sidebar_and_data_in_the_main_area` (the exact sidebar button order `sample, classify, reset`, nothing interactive in `at.main`), `test_file_problems_are_reported_in_the_main_area`, `test_download_rides_in_the_results_header_row`, `test_chart_shares_the_metric_row_above_the_results_table`, and `test_classify_click_announces_once_and_renders_in_the_main_area` (the cleared progress bar's `empty` slot in `at.main`, none in the sidebar — asserting "no `progress` element in the sidebar" is vacuous, since `process_dataframe` empties the bar before the run ends, and it passed with the bar drawn there). **Page config is invisible to AppTest**: `parse_tree_from_messages` skips every ForwardMsg without a `delta`, so `page_config_changed` never reaches `at`. `test_page_is_wide` therefore spies on the public `streamlit.set_page_config` (`patch(..., wraps=...)`; the script's `import streamlit as st` is the same module) and asserts `layout="wide"` and no `initial_sidebar_state`. Each of these was mutation-tested on 2026-09-23
- **Layout — geometry, measured headless on streamlit 1.64.0.** The sidebar is 300px expanded and 0 collapsed. For W ≥ 864, `stMainBlockContainer` has 80px side padding and a bordered card fills the block. A grid's `offsetWidth` is the card minus 32, and its `.dvn-scroller` `clientWidth` is 2px less. So with the sidebar open the card is W − 460 and the grid `clientWidth` is **W − 494**; collapsed, it is W − 194. Measured 606 / 786 / 946 / 1426 at 1100 / 1280 / 1440 / 1920 (1246 collapsed at 1440), the same for preview and results, and **with no maximum**: wide mode has no content cap. Below 864 the padding drops to 16px (768–863: W − 366 expanded, W − 66 collapsed), so the grid is non-monotonic: 497 at 863, 370 at 864, and not back to 497 until 991 (derived). At W ≤ 767 the main area is full width and an open sidebar overlays it. Against the retired centered layout's constant 670px grid, the two are equal at W = 1164 expanded (864 collapsed), and the new grid is narrower below that: 606 at 1100. **The overflow rule**: Streamlit sets `grow: 1` on every non-pinned column whenever the grid is stretched, capped columns included (`isStretched&&!isPinned&&{grow:1}` in the frontend's `DataFrame.*.js` chunk); glide then splits the spare width evenly across the growing columns (`floor(extra*grow/totalGrow)`, remainder to the last). So a grid overflows exactly when S, the sum of its columns' base widths, exceeds its `clientWidth`: below W = S + 494 expanded, or S + 194 collapsed (34 onsets checked 1px either side). Base widths: a capped long text column 300 (uncapped 500, glide's `maxColumnAutoWidth`), `id` 50 (glide's minimum), `label` 66, `Sentiment` (source or generated) 78, `Sentiment (model)` 126, `Confidence` 150. **Pinning changes the split, not S.** Pinned columns get no `grow`, so since the generated pair was pinned it keeps its base widths and the unpinned columns share all the spare width. Before pinning, the Sample results at 1920 read text 599 / `Sentiment` 377 / `Confidence` 450 — every column +~300 — and the review text stayed truncated on the widest screens; pinned, the text column gets 1426 − 228 = 1198 (derived). Short *source* columns are unpinned and still take an equal share (the two-column `text,Sentiment` preview gives the 8-character `Sentiment` column 602px at 1920). The same exclusion is why the preview orders its selected column first instead of pinning it. The server cannot see the viewport, so the cap cannot be made width-aware
- KPI metrics use `st.metric(..., border=True, width="content")` inside `st.container(horizontal=True)` (wraps on narrow screens — prefer over `st.columns` for metric/button rows, which forces fixed ratios and, since streamlit 1.63, ellipsizes a button label that does not fit its column — before 1.63 it wrapped the label onto two lines). **The distribution chart shares that row** as its last child: a bordered card that is the row's one stretching element, so it takes whatever width the content-sized cards leave, with `height=CHART_HEIGHT` (120) keeping the band near the cards' height. On its own full-width row the chart spent ~190px drawing two bars, and moved below the table it was off the bottom of the screen at every measured size. Content-width cards because stretched ones split the row unevenly by label length, and a card wrapped onto its own row filled all of it to show "3". At 1440 the chart card is comfortable, at 1280 it is squeezed to ~215px, and at 1100 it wraps onto its own row under the cards. The results `st.dataframe` sits below the band in its own bordered card; every card has a bold `st.markdown` label, as do the preview (`**Preview**`) and the landing page's `**Get started**`. The `**Results**` label shares a header row with an `st.caption` of the source name, `st.space("stretch")` and Download — the source because nothing else names the data after Sample, whose uploader stays empty. Material Symbols icons (`:material/...:`) on buttons and a `page_icon`
- **Every alert callout carries an `icon=`.** All five — the rename notice and the all-blank notice (`st.info`, `:material/info:`), the failed-read arm (`st.error`, `:material/error:`) and both unusable-CSV arms (`st.warning`, `:material/warning:`) — and so does the `Classification complete!` `st.toast` (`:material/check_circle:`) that replaced the sixth, an `st.success`, on 2026-09-23 (see the toast bullet). The three **failure** states were the only ones missing it until 2026-08-18, which was exactly backwards, and the reason it went unnoticed is that **Streamlit draws no default icon of its own**: `st.warning`/`st.error`'s docstring (unchanged from 1.61.1 through 1.64.0) is explicit that "If no leading icon is found, no icon is displayed", so those three rendered genuinely bare and carried their severity in fill color alone — the arms that most need to read as *something went wrong* read the most quietly. **Pinned as of 2026-08-18, and the first draft of this bullet got that wrong.** The claim was that it *could not* be pinned, which is true only of the assertions that already exist: `AlertBase.value` returns `proto.body`, so all seven flow-test body-substring matches stayed green straight through the fix. But `Element.__getattr__` falls back to `getattr(self.proto, name)` (`streamlit/testing/v1/element_tree.py`), so `at.warning[0].icon` reads the field directly — verified: `Warning(Alert(body="x", icon=":material/warning:")).icon` returns `":material/warning:"`. `test_unusable_csv_still_offers_reset` and `test_malformed_upload_offers_reset` now assert it on the three states that were bare, and both were mutation-tested (drop one `icon=` → red, restore → green). The two `st.info` calls are deliberately left unpinned, having never regressed; the toast's icon is pinned by `test_completion_is_a_toast_on_the_classify_run_only`, which asserts the call whole. **Re-check the census with an AST walk, not a grep**: five of the six calls are multi-line, so `grep -n 'st\.\(info\|warning\|error\|success\)(' streamlit_app.py` prints the call line and leaves `icon=` two or three lines below it — it reports five apparently bare callouts on code that is entirely correct, and would read identically if a seventh genuinely bare one were added. That grep was prescribed here for one commit, which is the same truncating-filter trap this repo has hit before. Use `uv run python -c "import ast; [print(n.lineno, n.func.attr, next((k.value.value for k in n.keywords if k.arg=='icon'), None)) for n in ast.walk(ast.parse(open('streamlit_app.py').read())) if isinstance(n, ast.Call) and isinstance(n.func, ast.Attribute) and n.func.attr in {'info','warning','error','success','toast','exception'}]"`, which also covers the `st.toast`/`st.exception` spellings the grep never named
- **`Classification complete!` is an `st.toast` on the run that classified, not a persistent `st.success`.** `_render_results` re-renders on every rerun that keeps results on screen, so the callout announced completion again after any unrelated rerun — switching the column away and back included, with nothing classified — and spent a 75px band above the table saying so (grid top 494 → 419 at 1440×900, headless). `_render_results(..., announce=False)` takes the caller's `classify_clicked` and fires the toast only when it is true, and only in the non-blank arm, so an all-blank run is never called complete. It defaults, unlike the generated pair (see the plumbing bullet), because the default *is* the common case — the re-render — and a wrong value costs a toast, not a wrong column. - **Output-name collisions — the rule.** `process_dataframe` never writes a literal `result["Sentiment"]`; that assignment is an in-place replace in pandas with no error and no warning, which is why a CSV carrying a ground-truth `Sentiment` column used to lose it silently in the table *and* the download. It resolves both output names against the *input* frame via `_generated_columns` — the single definition of the rule, the way `_is_text_dtype` is the single definition of "text column" — and returns them as a `GeneratedColumns(sentiment, confidence)` NamedTuple. The plain names are used whenever they are free, so the common path is byte-identical: same headers on screen, same headers in the download, same column order. **"Free" means the whole `(model)` name space is free, not just the base string.** `_unique_column_name` asks `_namespace_members` — which matches `base` exactly plus anything under the `base (model)` prefix — rather than testing `base not in taken`, because a source column already called `Sentiment (model)` holds the user's data under the header this app uses to mean "the model's output". Checking only the base returned a bare `Sentiment` for the *prediction* there, inverting the convention with no notice at all, since nothing registered as a collision; reachable from a downloaded result whose ground-truth column was dropped before re-uploading. `taken` is therefore iterated (`Collection[object]`), not merely probed (`Container[object]`) — an infinite name space cannot be decided by membership tests. The counted case one level deeper is covered too: a lone `Sentiment (model) 2` reserves the space and the prediction takes the free bare `Sentiment (model)` slot, so both columns end up suffixed — odd-looking, but never mistakable for the user's data, which is the property that matters
- **Output-name collisions — the direction, and why it is the fix.** On a collision the **model's** column is renamed to `Sentiment (model)` (then ` 2`, ` 3`, …) and the user's column keeps its data, its name and its position; the result is always the input frame **plus** two columns. The mirror-image scheme (keep `Sentiment` for the prediction, push the source column to `Sentiment_1`) preserves every value and was still **rejected**: the download's `Sentiment` header would silently change meaning from ground truth to prediction, so an eval script keyed on it compares predictions to predictions — the same class of silent, plausible, wrong as the original bug, just relocated one layer up. `(model)` rather than `_1` because the header is the only explanation that travels with the downloaded file, and `_1` reads as a duplicate of the user's column rather than as the model's output. Round trips are lossless and monotonic: re-classifying a downloaded result appends and displaces nothing (`text, Sentiment, Confidence` → `+ Sentiment (model), Confidence (model)` → `+ Sentiment (model) 2, …`), and that holds even when the intermediate columns are deleted between passes, which is what the name-space rule above buys
- **Output-name collisions — the plumbing.** `_render_results` takes the pair as a **required** third argument and unpacks it immediately, so its nine lookups still read as plain column names and any 2-tuple works — which is what lets the flow tests hand-seed one. - **Results table — the cap is length-aware, not dtype-only.** `_is_long_text(series, name)` gates the width cap on `LONG_TEXT_CHARS = 50`, and the threshold is **measured, not guessed**: rendering one `width="content"` text column at a range of lengths puts its natural width at 281px for 48 characters and 305px for 52, so auto-sizing crosses `TEXT_COL_WIDTH` at ~51. Confirmed in the emitted spec. Only the hub cache is missing here (it is restored in the `integration` job), so `check` re-fetches `load_model`'s ~1.2 MB of config/tokenizer files on every run: the job needs network, just not the checkpoint. A second `integration` job (`needs: check`, `timeout-minutes: 30`) runs `pytest --integration -m integration` against the real checkpoint, with `~/.cache/huggingface/hub` cached (covers both the download and the safetensors conversion). No `HF_TOKEN` secret is *required* — the model is public — but one is passed through if present, since anonymous downloads from shared Actions IPs are what get rate-limited; `load_model`'s `or None` turns the empty value of a missing secret back into an anonymous request. The cache key is exact and static, so it never self-refreshes: bump its `-v1` suffix if upstream moves `main` to a new revision
  - Workflow-level `permissions: contents: read` in both workflows; only the job that publishes re-grants itself `contents: write`. `concurrency` keeps a plain `cancel-in-progress: true`: making it PR-only does **not** guarantee every `main` commit gets a run, because [GitHub cancels any previously *pending* run in the group regardless of that setting](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency) (only `queue: max` changes that), and it would serialize every `main` push behind the 30-minute `integration` job. The `release` job's tag check makes a superseded run harmless anyway
  - Action versions are deliberately non-uniform: `actions/checkout@v7` and `actions/cache@v6` track floating major tags, but `astral-sh/setup-uv` is pinned to the **exact** `@v10.2.0` because upstream stopped publishing major/minor tags at v8 (citing the tj-actions supply-chain attack), so `@v10` does not exist. That pin needs manual bumping, and a stale one is a supply-chain gap rather than a missed feature: nothing here pins a uv version, so CI installs the latest uv, and up to v10.0.1 the action verified the download only against a checksum list bundled into that release — a uv newer than the list was installed **unverified** (`core.debug` and return). v10.1.0 added a fallback to `astral-sh/versions` checksums (#1033). Bumped from v10.0.1 in the 2026-09-23 upgrade; the only input default that moved is `save-cache` (`auto`, which skips saves on `merge_group` events), and nothing here uses a merge queue. `prune-cache` is left at v10's `false` default rather than restored to the pre-v9 `true`: `uv cache prune --ci` strips pre-built wheels and keeps only wheels built from source, and every dependency here ships a pre-built wheel — so `true` persisted an almost-empty cache and re-downloaded the set every run, which is exactly why upstream flipped the default
  - `cache-dependency-glob` is deliberately **not** set. The action's default is a 7-pattern list that already includes `**/pyproject.toml` and `**/uv.lock` (true since v6), so the `cache-dependency-glob: uv.lock` this repo used to carry *narrowed* the key by dropping `pyproject.toml` — a pyproject-only change (a new dependency group, a changed `requires-python`) could then restore a stale cache. `enable-cache: true` **is** still explicit, because the `auto` default disables caching on tag-push and release events
- A third `ci.yml` job, `release` (`needs: [check, integration]`, `ubuntu-latest`), publishes a GitHub Release the moment a bumped `[project].version` lands green on `main` — gated on both jobs, so a release is never cut from unverified code. Its `if:` asserts `github.ref == 'refs/heads/main'` explicitly rather than inheriting main-only from `on.push.branches`, so widening that trigger later cannot leak a public release out of an unreviewed branch. It reads the version with `uv version --short` (no sync needed; it only parses `pyproject.toml`, verified against a project with no `.venv` and no lockfile)
  - Idempotent on **tag existence**, not on a `git diff HEAD^`: a diff misses a bump arriving behind a merge commit's second parent and re-fires on a workflow re-run. The *tag* rather than the release, because deleting a release to re-cut it by hand leaves the tag behind, and that tag is the signal for the job to stay out of the way
  - The tag list is assigned to a variable **before** being tested, never piped straight into `grep`: a transient API error must abort the job under `set -e` rather than read as "no tag found" and fall through to an unconditional `gh release create`. Fail closed, not open
  - `--target "$GITHUB_SHA"` deliberately tags the commit *this run verified*, which need not be the commit that bumped the version — if the bump's own run was superseded, the release is cut from the newer tested tree rather than an untested one. A PEP 440 pre-release (`0.8.0rc1`, `0.9.0.dev1`) gets `--prerelease` so it cannot take the "Latest" slot or the README's `sort=semver` tag badge
  - `gh release create --target` creates the tag itself and `--generate-notes` builds notes server-side, so a shallow checkout and no tag push are enough
- `.github/workflows/release.yml` (`on: push: tags: v*`) is now only the **manual escape hatch** — re-cutting a deleted release, or tagging an older commit. It cannot double-publish against the `release` job: that job's tag is created with the `GITHUB_TOKEN`, and [GitHub does not start a workflow run from a `GITHUB_TOKEN` event](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) (only `workflow_dispatch`/`repository_dispatch` are exempt). That suppression is no longer *load-bearing*, though: `release.yml` now does its own existence check (on **releases**, since the tag necessarily exists by the time it fires) and no-ops instead of going red, so each path is independently safe to run twice. That was not merely defensive — two routes already reached it with no PAT involved: force-pushing an existing tag re-fires `on: push: tags`, and re-running an old workflow run replays it. Merging the two paths behind a `workflow_dispatch` was considered and **rejected**: `ci.yml`'s job is `needs: [check, integration]`, so routing the manual path through it would re-run today's CI against the old code you are re-cutting, making the escape hatch least reliable exactly when it is needed

The README shows **one** screenshot, `docs/screenshot-dark.png`. There was a light/dark pair in a two-column table until 2026-08-15; the light shot was deleted rather than recaptured, so do not re-add a `docs/screenshot-light.png` reference on the assumption the file went missing by accident.

**Recaptured 2026-09-23 and current**, at **1440×865**, for the sidebar + wide layout (the previous 800×1433 shot showed the retired centered layout). The height moved 1433 → 865 because the controls left the main column, the chart joined the metric row and the success callout became a toast, so **always re-measure `stMain.scrollHeight` per the traps below rather than reusing a recorded number** — including the 865 in this sentence.

It is captured by **`docs/capture_screenshot.py`** (checked in 2026-08-18; before that there was no script and each recapture was rebuilt from this section):

```bash
uv run streamlit run streamlit_app.py                              # one shell
uv run --with playwright python docs/capture_screenshot.py [port]  # another
```

It drives the **system** Chrome (`chromium.launch(channel="chrome")`, so no browser download), loads the sample via **Sample** and clicks **Classify** (both in the sidebar now; the `button:has-text(...)` locators are block-agnostic, and the Get started card's bold **Sample**/**Classify** are markdown, not buttons) — the README's alt text says "classifying sample data" — then waits for the `Classification complete!` toast to detach (~4s) so the shot shows the state the user is left with, and parks the pointer off Classify so the button is not captured in its hover color, and writes next to itself, so it works from any working directory. Playwright is deliberately **not** a project dependency: it is a manual tool run a few times a year, and `--with` keeps it out of `uv sync` and CI. The cost of that choice is one `# ty: ignore[unresolved-import]` on its import, which **is** load-bearing (verified: removing it fails `ty check .`), and is now the only `ty: ignore` in the repo. The script encodes every trap below, so prefer editing it over rewriting a capture from scratch. Four traps, all found the hard way:

- **Dark mode comes from `color_scheme="dark"` on the browser context**, not a flag. With no `.streamlit/config.toml` the app follows `prefers-color-scheme`, so this exercises the real default-theme path; `streamlit run --theme.base=dark` would instead re-introduce a custom theme and screenshot something the app does not ship
- **`full_page=True` silently returns a viewport-height image.** Streamlit scrolls an inner `overflow: auto` element, so the document never grows. The scroller is `<section data-testid="stMain">` — **not** `stAppViewContainer` (its `scrollHeight` equals the viewport) and **not** `document.body` (`scrollHeight` is literally `0`). Measure `stMain.scrollHeight`, resize the viewport to it, then capture. That number still overshoots by the shell's bottom spacer (~400px of dead air below `Download`), so trim to `stMainBlockContainer.lastElementChild`'s `getBoundingClientRect().bottom`
- **Headed capture draws a real scrollbar into the frame.** `headless=False` is worth using (it renders on the actual display rather than offscreen), but macOS Chrome then paints a scrollbar for `stMain`'s residual overflow — `scrollHeight` stays ~160px past the trimmed viewport because of the shell's bottom spacer — and it both lands in the shot and narrows the main area, and the results grid in it, by its own width. Kill it on the page scroller only (`section[data-testid="stMain"]`, `scrollbar-width: none` plus a zero-width `::-webkit-scrollbar`); the results grid keeps its own, which is a real affordance. Headless does not show this, so a headless-captured shot and a headed one are not interchangeable. Two further headed-only notes: a headed window **cannot exceed the physical screen**, so `set_viewport_size` can come back short and clip the capture exactly the way `full_page=True` does — read `window.innerWidth`/`innerHeight` back and fall back to CDP `Emulation.setDeviceMetricsOverride`, which is not window-bounded. Width matters too now that the script asks for 1440, which a scaled display can undercut. The fallback was not needed for the 1440×865 capture on this machine; check rather than assume; and the context viewport also emulates `window.screen`, which reports the viewport rather than the display
- **Width is a real choice now, and the script uses 1440.** Under the centered layout, width above ~800 bought nothing: content was capped at 736px, so extra width only added side margin. `layout="wide"` has no cap: with the 300px sidebar open and W ≥ 864, the grid's `clientWidth` is W − 494 (see the geometry bullet in Key Patterns). 1440 is a common laptop viewport and the narrowest where the distribution chart in the metric row gets a comfortable card — at 1280 it is squeezed to ~215px, and at 1100 it wraps onto its own row. Wider buys little for the README: GitHub scales the image down to its column, so extra width only shrinks the text. Never capture below 864, where the padding breakpoint makes the grid non-monotonic, or below 768, where an open sidebar overlays the main area. The retired pair was 596 wide, which worked only under the custom theme's `baseFontSize = 14`; at the default 16px that width wraps the metric row 3+1 and pushes `Sentiment`/`Confidence` off-canvas, so do not go back to it. Hide the app chrome first (`header`, `stToolbar`, `stStatusWidget`; a former `stDecoration` rule was dropped 2026-09-23 because no such test id exists in the 1.61.1 or 1.64.0 frontend bundle, so it never matched anything) and tighten `stMainBlockContainer` padding, or the toolbar lands in the frame. `header` matches only `stHeader`, the main-area toolbar, which does not contain the sidebar. The sidebar's own header (`stSidebarHeader`, holding the `«` `stSidebarCollapseButton`) is not a `<header>` element, sits inside `stSidebar` and stays in the shot; it is the real way to collapse the sidebar

**A regression this surfaced, since fixed:** at the default 16px font the results grid wanted 728px but got 670px, so the `Confidence` percentage was cut off and needed horizontal scrolling. Under the centered layout that was the app's real behavior at *every* window width (the 736px content cap made it width-independent), not a capture artifact. It appeared the moment the custom theme's 14px font went away. The fix is `TEXT_COL_WIDTH` on free-text columns (see the results-`dataframe` bullet in Key Patterns), measured 728 → 670 against a 670px `clientWidth`. `layout="wide"` was rejected *as that fix*, since it would restyle every element on the page to undo a 58px overflow. It was later adopted for the sidebar layout, which does **not** retire the cap: 728 is the uncapped Sample's S, and with the sidebar open the grid is only 606 at a 1100px window. Uncapped, the Sample overflows below 1222; capped, below 1022. Verify any change to the cap against **both** `mixed_sample.csv` and `blank_cells.csv` at a laptop width with the sidebar open. 400px overflows both at 1100 (628/606, 678/606), and under the centered layout it passed the single-column sample and still overflowed the two-column one by 8px.
