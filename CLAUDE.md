This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**SiEBERT MLX** (`siebert-mlx`) is a Streamlit application for sentiment classification in English text using SiEBERT (`siebert/sentiment-roberta-large-english`) on Apple Silicon with MLX. Users upload a CSV (or try the built-in sample data), select the text column, classify, and download results with added "Sentiment" and "Confidence" columns — renamed to "Sentiment (model)" / "Confidence (model)" when the CSV already uses those names, so source data is never overwritten. Guided step-by-step UI with auto-detected text columns, summary metrics (including a `Skipped` card when the file has blank text cells), and a Reset button — available from every state a loaded file can reach — to start over.

## Architecture

Single-file application (`streamlit_app.py`, ~800 lines):

1. **`detect_text_column`** — returns first string- or object-dtype column name via `next()` generator. The dtype predicate itself lives in **`_is_text_dtype`** (`pd.api.types.is_string_dtype` / `is_object_dtype`, matching the pandas 3.0 default `str` dtype), shared with `_render_results`' column-width cap so "what counts as a text column" has exactly one definition
2. **`_ensure_safetensors`** — downloads model via `snapshot_download` (prefers `model.safetensors`, falls back to `pytorch_model.bin`), converts to safetensors if needed; `torch` and `safetensors` are lazy-imported only when conversion is required. The conversion writes to a sibling `model.safetensors.*.tmp` and `os.replace`s it into place — the `exists()` guard means a truncated destination would be accepted forever, so the write has to be all-or-nothing; the `finally` unlink covers every failure path and is a no-op once `replace` has consumed the temp file
3. **`load_model`** — loads config via `AutoConfig`, constructs `RobertaForSequenceClassification`, loads weights via `from_pretrained` with `float16=True` (weight **memory** only — since mlx-transformers 0.3.0, `get_extended_attention_mask` hardcodes a `mx.float32` additive mask, which promotes every encoder activation, so `.logits` come back `float32` and compute is fp32 regardless; there is no input-side lever, `roberta.py` never passes `dtype`), then `mx.eval(model.parameters())` to materialize the lazy weights on the loading thread; cached with `@st.cache_resource(show_spinner="Loading model...", show_time=True)`; authenticates with `HF_TOKEN`. The spinner text lives **on the decorator, not in a `with st.spinner(...)` around the call**: `show_spinner` defaults to `True`, so wrapping the call stacked two spinners on a cache miss — the app's plus Streamlit's own ``Running `load_model()`.``, which leaks an internal symbol onto the one screen that is otherwise empty. `show_time=True` because a cold cache is a ~1.4 GB download plus the safetensors conversion, and a static spinner for minutes is indistinguishable from a hang. The **call site** is below the page chrome (see the UI bullet), not next to this definition
4. **`process_dataframe`** — pre-filters blanks, **sorts the surviving rows by text length**, batches them (`BATCH_SIZE=8`), tokenizes with `return_tensors="np"` and converts to `mx.array`, classifies via softmax over logits; uses `.tolist()` for batch conversion; clears its `st.progress` bar (`progress_bar.empty()`) when done. The sort (`valid.sort(key=lambda pair: len(pair[1]))`) is a padding optimization, not a semantic one: each batch is tokenized with `padding=True`, i.e. padded to the longest sequence *in that batch*, so in file order one long review drags the other seven rows through all 24 encoder layers at its width — attention being quadratic in that width. Sorting confines long rows to their own batches. Character length is a free proxy for token length. **Row order in the returned frame is untouched** — `indices` still carries the original positions and the write-back is by `idx`, never by batch position (`test_batching_preserves_original_row_order`). Returns a **2-tuple**, `(result, GeneratedColumns(sentiment, confidence))`, not a bare frame: the two appended column names are conditional on the input, so the function that writes them is also the one that reports them (see the collision bullets in Key Patterns)
5. **UI** — guided step-by-step flow: title + orienting `st.caption` → file upload or sample data → column auto-detect and preview → classify → metric cards + sentiment-distribution bar chart + styled results table → CSV download. Results are stored in `st.session_state` and re-rendered from there, so post-classify reruns don't re-run inference. **`load_model()` is called below the chrome** — after the uploader and Sample button, before the upload handler — not at the top of the script. Nothing above the classify branch needs the model, but Streamlit emits deltas as the script runs, so loading first meant the page body was *nothing but* a spinner until the weights were ready: no title, no uploader, nothing to click. That is minutes on a cold cache and still the fp16 load plus `mx.eval` on every fresh process, and it is not one-session-only — `st.cache_resource` holds a compute lock (`cache_utils.py`: "only one of those sessions computes the value, and the others block"), so every session connecting during the first load gets the same empty page. Kept **eager** rather than moved into the classify branch so the load still overlaps with the user choosing a file (the uploader posts to `/_stcore/upload_file`, which does not wait on the script thread), and so `streamlit_app` still calls `load_model()` at import — which is what `tests/conftest.py`'s module-level patches exist to intercept

## Key Patterns

- MLX for all inference on Apple Silicon (no device management needed)
- MLX streams are thread-local; Streamlit runs each rerun on a fresh thread, so `load_model` must `mx.eval(model.parameters())` to materialize the weights before caching. Skipping this leaves the float16 weights as pending ops bound to the loader thread's GPU stream, and the first classify (a later rerun thread) fails with `RuntimeError: There is no Stream(gpu, 0) in current thread.`
- `hf_logging.set_verbosity_error()` suppresses expected checkpoint warnings
- Confidence via `mx.softmax(logits, axis=-1)` with `mx.max` and `mx.argmax`; `mx.eval()` before `.tolist()`; labels from `model.config.id2label`
- Empty, whitespace-only, and missing (`NaN`) texts skipped; get sentiment `""` and confidence `0.0` (`fillna("")` before `astype(str)` coerces pandas 3.0 missing cells, which no longer stringify to `"nan"`)
- Tokenizer uses `return_tensors="np"` converted to `mx.array`, with `truncation=True` (512 token limit) and `padding=True`
- `process_dataframe` returns a copy; input DataFrame is not mutated
- `st.session_state` persists the loaded DataFrame (`df`/`source_name`) and the classification result (`result_df`/`result_col`/`result_generated_cols`) across reruns, so a post-classify rerun (Download click, theme toggle) re-renders from state instead of re-running inference; the result is invalidated when the selected column no longer matches `result_col`. The three `result_*` keys are written in one branch and popped together by `_clear_results` — `result_generated_cols` names columns *inside* `result_df`, so a survivor would be applied to the next file's results. Do not confuse it with `result_col`, which is the **input** text column. They can still come apart across a **code** change, which is why `"result_generated_cols" in st.session_state` is part of the render guard rather than assumed: streamlit's file watcher reruns an edited script against the session_state already in memory, so a session holding results from before that key existed hit an uncaught `KeyError` and rendered a traceback in place of the page. The guard degrades it to the pre-classify view; the lookup inside stays an index, not a `.get()` default, because a default of the plain names would tint, size and count the user's own `Sentiment` column on exactly the input the indirection exists for. `test_results_missing_the_generated_pair_degrade_instead_of_crashing` pins it
- `Sample`/`Reset` are `on_click` callbacks (mutate `session_state` before the rerun, no `st.rerun()`); `Classify` still uses the `st.button`-returns-`True`-only-once-after-click pattern (`classify_clicked`)
- Uploaded files load once, guarded on `uploaded_file.file_id`, and the uploader has a dynamic `key=f"uploader_{...}"` that `Reset` increments — without both, the persisted uploader value re-reads on every rerun, undoing `Reset` and clobbering a `Sample` pick
- **The has-file → no-file transition has its own arm.** `elif uploaded_file is None and "_uploaded_id" in st.session_state:` pops `_uploaded_id`, `df`/`source_name` and the results. Clicking the uploader's **X** makes `st.file_uploader` return `None`, which fails the `file_id` guard above, so the whole branch was skipped and `df` was read straight back out of `session_state` — leaving the preview, metrics, chart, results table and a Download button all describing a file the uploader now reported as absent. Same rule the failed-read arm already enforces, applied to the one transition nothing else observed. **Guarded on `_uploaded_id`, not a bare `is None`**: the uploader is empty by construction on the rerun that `_load_sample` populates `df`, and both `_load_sample` and `_reset` pop `_uploaded_id` via `_reset_uploader`, so neither path can reach here and wipe the data it just loaded — widening it to a bare `is None` fails `test_sample_button_populates_session_state`, `test_stale_upload_does_not_override_sample` and `test_sample_survives_the_empty_uploader_it_is_loaded_alongside`. Popping the id rather than calling `_reset_uploader()` is deliberate too: bumping `uploader_key` would remount an already-empty widget. `test_removing_the_uploaded_file_clears_data_and_results` pins the arm itself
- **The text-column selectbox is keyed to the loaded dataset**, `key=f"text_column_{uploader_key}_{_uploaded_id or 'sample'}"`. Unkeyed, its widget identity is a hash of `(label, options, index, help, ...)` (`elements/widgets/selectbox.py` → `compute_and_register_element_id`), so two files with the same header list **and** the same auto-detected column shared one widget: a manual override on the first was silently reapplied to the second, and `index` — the auto-detect — was ignored. That rule was an implementation detail of Streamlit's id computation rather than anything this app chose. Keying on the load makes it explicit: every new upload, `Sample` or `Reset` mints a fresh widget, so auto-detect applies to every file. Both inputs are available by then — `uploader_key` from the `setdefault` near the title, `_uploaded_id` written before this branch renders. `test_auto_detect_reapplies_to_a_file_with_the_same_headers` pins it
- A failed `pd.read_csv` (`ParserError`/`EmptyDataError`/`UnicodeDecodeError`/`ValueError`) pops `df`/`source_name` and the results before showing `st.error` — a rejected upload must not leave the previous file's preview and results on screen as if they were its own. `_uploaded_id` is advanced **only** in the `else` arm: leaving it stale is what re-renders the error on the next benign rerun instead of letting it vanish, and `test_malformed_upload_shows_error_and_clears_data` / `test_upload_error_persists_across_reruns` pin both halves
- Walrus operator (`:=`) in UI guards to combine detect + check into one `elif`
- `SAMPLE_DATA_PATH` points to `samples/mixed_sample.csv` for the "Sample" button
- KPI metrics use `st.metric(..., border=True)` inside `st.container(horizontal=True)` (content-sized, wraps on narrow screens — prefer over `st.columns` for metric/button rows, which forces fixed ratios and can wrap a button label onto two lines); the distribution `st.bar_chart` and results `st.dataframe` sit in bordered `st.container(border=True)` cards with bold `st.markdown` labels; Material Symbols icons (`:material/...:`) on buttons and a `page_icon`
- **Every alert callout carries an `icon=`.** All six — the rename notice and the all-blank notice (`st.info`, `:material/info:`), `Classification complete!` (`st.success`, `:material/check_circle:`), the failed-read arm (`st.error`, `:material/error:`) and both unusable-CSV arms (`st.warning`, `:material/warning:`). The three **failure** states were the only ones missing it until 2026-08-18, which was exactly backwards, and the reason it went unnoticed is that **Streamlit draws no default icon of its own**: `st.warning`/`st.error`'s 1.61.1 docstring is explicit that "If no leading icon is found, no icon is displayed", so those three rendered genuinely bare and carried their severity in fill color alone — the arms that most need to read as *something went wrong* read the most quietly. **Pinned as of 2026-08-18, and the first draft of this bullet got that wrong.** The claim was that it *could not* be pinned, which is true only of the assertions that already exist: `AlertBase.value` returns `proto.body`, so all seven flow-test body-substring matches stayed green straight through the fix. But `Element.__getattr__` falls back to `getattr(self.proto, name)` (`streamlit/testing/v1/element_tree.py`), so `at.warning[0].icon` reads the field directly — verified: `Warning(Alert(body="x", icon=":material/warning:")).icon` returns `":material/warning:"`. `test_unusable_csv_still_offers_reset` and `test_malformed_upload_offers_reset` now assert it on the three states that were bare, and both were mutation-tested (drop one `icon=` → red, restore → green). The `st.info`/`st.success` pair is deliberately left unpinned, having never regressed. **Re-check the census with an AST walk, not a grep**: five of the six calls are multi-line, so `grep -n 'st\.\(info\|warning\|error\|success\)(' streamlit_app.py` prints the call line and leaves `icon=` two or three lines below it — it reports five apparently bare callouts on code that is entirely correct, and would read identically if a seventh genuinely bare one were added. That grep was prescribed here for one commit, which is the same truncating-filter trap this repo has hit before. Use `uv run python -c "import ast; [print(n.lineno, n.func.attr, next((k.value.value for k in n.keywords if k.arg=='icon'), None)) for n in ast.walk(ast.parse(open('streamlit_app.py').read())) if isinstance(n, ast.Call) and isinstance(n.func, ast.Attribute) and n.func.attr in {'info','warning','error','success','toast','exception'}]"`, which also covers the `st.toast`/`st.exception` spellings the grep never named
- **The metric row is four cards, or five.** `Total rows` / `Positive` / `Negative` / `Avg confidence`, plus a **conditional** `Skipped` card rendered only when `skipped = total - len(classified)` is non-zero. Positive and Negative divide by `total` while `avg_conf` averages over `classified`, so skipped rows are inside the denominator of the two percentages and they visibly fall short of 100 — on `samples/blank_cells.csv` they read 40% and 30%, with the other 30% unexplained anywhere on the one part of the page whose job is to summarize the run. The fix names the remainder rather than changing the denominators: `Total rows` should keep meaning rows in the file, and an average confidence over rows the model never scored would be meaningless, so `classified` stays the only defensible denominator for `avg_conf`. **Conditional is load-bearing**: three flow tests pin `len(at.metric) == 4` (`test_results_persist_from_session_state_without_reclassify`, `test_large_result_skips_styler_without_error`, `test_collision_renames_the_model_column_and_metrics_follow_it`), and an unconditional fifth card would also give every clean file a permanently-zero metric. `test_skipped_rows_get_their_own_metric` and `test_no_skipped_metric_when_every_row_classified` pin both halves
- **The landing page carries an `st.caption`** under the title stating what the app does and what it wants ("Upload a CSV with a text column — text longer than 512 tokens is truncated"). Every requirement used to surface only as a post-hoc rejection ("No text columns detected") *after* the user had chosen a file, and the 512-token truncation was invisible everywhere in the UI. `st.caption` not `st.info`: this is orienting metadata, not an instruction, and this app reserves callout weight for things that actually happened
- **`_clear_data()` is the one "forget the loaded file" rule**, popping `df`/`source_name` and calling `_clear_results()`. Three sites need it — `_reset`, the failed-read arm and the uploader's has-file → no-file arm — and it was written out longhand in all three, so a fourth loaded-file key would have meant remembering three unrelated places. Same reasoning that produced `_clear_results` for the `result_*` trio
- **The failed-read arm renders `_reset_button()` too**, and needs it most: it pops `df`, so the `if df is not None:` block never runs and none of *its* three call sites fire, while its `st.error` is deliberately sticky (`_uploaded_id` is left stale so the error survives benign reruns). Without it the only exits were the uploader's ✕ and Sample. `_reset()` rather than a bare `_clear_data()` because it also bumps `uploader_key`, remounting an empty uploader — which is what actually retires the stale id and the error with it. `test_malformed_upload_offers_reset` pins it
- **`_reset_button()` is a helper, called from all four arms** of the `if df.empty / elif no text column / else` branch. Reset used to render only alongside Classify in the `else` arm, so a file that loaded but could not be classified showed a dead-end warning — the two arms that most need an escape were the two without one. One `key="reset"` across all three call sites is safe because the arms are mutually exclusive, so exactly one renders per run. `test_unusable_csv_still_offers_reset` pins it for both warnings
- **Results table — rendering.** `st.dataframe` uses `column_config` (`ProgressColumn` for the resolved confidence column as `format="percent"`, `TextColumn` for the resolved sentiment column) with `hide_index=True`. Neither entry passes an explicit label: `st.column_config` documents `label=None` as "the column name is used", so the header self-syncs with the frame and a renamed `Sentiment (model)` can never disagree with the downloaded CSV. Per-value coloring of the resolved sentiment column is a Pandas `Styler.map` tint instead — formatting via `column_config`, coloring via Styler, per Streamlit guidance. Both `st.dataframe` calls (results and preview) pass **`placeholder=""`**: the default renders a missing cell as the literal word `None`, and `process_dataframe`'s `fillna("")` applies to the local `texts` list rather than to the frame, so `result = df.copy()` keeps the source column's real `NaN` — the grid then contradicted itself on the same row, printing `None` for the user's blank text beside a genuinely empty generated `Sentiment` cell. `samples/blank_cells.csv` is exactly that shape, and its NA rows fall inside the preview's `.head()`
- **Results table — the tint is capped on rows *and* cells.** The guard is `len(result_df) <= STYLE_ROW_CAP and result_df.size <= int(pd.options.styler.render.max_elements)`. The first clause is a cost judgement (a per-cell style for every row defeats `st.dataframe`'s virtualization); the second is a **hard limit** and not a second opinion. Streamlit rejects a Styler on `styler.data.size > pd.options.styler.render.max_elements` (`elements/lib/pandas_styler_utils.py:51`; 262,144 under pandas 3.0.5), i.e. on **cells**, while `STYLE_ROW_CAP` counts **rows** — so a frame under 2000 rows but over the cell budget (>131 columns at 2000 rows, >262 at 1000, >524 at 500) passed the guard, got wrapped, and raised `StreamlitAPIException` inside `st.dataframe`. Nothing catches it: `arrow.py:1115` calls `marshall_styler` with no enclosing try/except, so **the script aborted** — reproduced at 2000×140, rendering zero dataframes and zero download buttons, i.e. the user lost the results table *and* the download after paying for the classification. Note the asymmetry that hid it: the tint is applied to **one** column via `subset=`, but the limit counts the whole frame. `<=` rather than `<` because streamlit raises on `>`, so a frame sitting exactly on `max_elements` is legal and keeps its tint. `test_wide_result_under_the_row_cap_still_renders` pins the wide case; `test_large_result_skips_styler_without_error` pins the tall one and **still passes with the cell clause reverted**, which is why both are needed
- **Results table — column widths.** Every **long** source column gets `st.column_config.Column(width=TEXT_COL_WIDTH)` (300px), built as a dict comprehension over `result_df.columns` with the two generated keys assigned on top afterwards. Without a `width` a column is "sized to fit the cell contents", so one long review pushes `Confidence`'s percentage out of the grid; leftover space redistributes evenly, so the table still fills its card. **The base `Column`, not `TextColumn`** — this is the whole reason the comprehension has no dtype clause. `TextColumn(width=300)` emits `{'width': 300, …, 'type_config': {'type': 'text', …}}`, i.e. setting a width *also declares the column's type*, so capping a numeric column meant rendering its numbers as text; `Column(width=300)` emits `{'width': 300, …}` with no `type_config` at all and leaves the inferred type alone (verified against streamlit 1.61.1). The old `_is_text_dtype` clause existed to dodge that coupling, not to state a layout fact, and dropping it turned the one shape the clause caught but could never fix — a numeric column under a >50-char header — from uncappable into ordinary: measured 1004/670 → 828/670. Still overflowing, because four columns at that width simply do not fit, which is the documented correct outcome; the point is that the column is now capped like any other rather than excluded by construction. Three properties follow, all load-bearing: it caps *every* qualifying column rather than only the classified one (a second free-text column blows the same budget, which is why no `text_col` argument is threaded in); it leaves **short** columns auto-sized via `_is_long_text`, because padding a 2-char `id` — or an 8-char label — out to 300px would spend the very budget the cap protects (see the length-aware bullet below); and the exclusion tuple holds the **resolved** generated names, which is what makes it collision-proof now — under a collision the *preserved source* `Sentiment` column is free text of unknown length and correctly **gets** the cap, while the model's renamed column keeps its own config (assigning the generated keys last is now belt-and-braces rather than the guarantee). 300 rather than `"large"` (400) because 400 left **zero** slack — measured `scrollWidth` 678 against a 670px `clientWidth` on `samples/blank_cells.csv` (`id,text`), i.e. it only ever fixed the single-column case it was tested on, while 300 measures 670/670 on both that and `mixed_sample.csv`. Past roughly three text columns no fixed width can prevent a horizontal scroll, and that is the correct outcome. `TestRenderResultsColumnConfig` pins this against the kwargs passed to `st.dataframe` — our own call, not a Streamlit proto, so it does not churn across versions; each of the comprehension's two clauses is pinned by a *different* pair of its ten tests, measured one clause at a time: dropping `_is_long_text` fails `test_leaves_short_text_columns_auto_sized` and `test_does_not_cap_a_short_source_sentiment_column`; leaving the exclusion tuple literal fails `test_caps_the_preserved_source_column_not_the_generated_one` and `test_keys_both_generated_columns_when_both_are_renamed`. `test_caps_a_numeric_column_under_a_long_header` is what would fail if a dtype clause were ever re-added — int64/float64 values top out at 19 and ~24 characters and so can never reach `LONG_TEXT_CHARS` on their own, which makes a long column *name* over numeric values the only shape that distinguishes the two rules. `test_caps_the_free_text_column` additionally asserts `Column` rather than `TextColumn`, so a revert to the type-declaring form fails there. `test_keys_both_generated_columns_when_both_are_renamed` is also the *only* thing pinning `column_config[confidence_col]`: with the confidence name left plain, a mutant keyed to the literal lands on the same key and nothing fails. The sibling class `TestRenderResultsGeneratedColumns` pins the other side: metrics, tint, all-blank guard and notice all follow the resolved names
- **Output-name collisions — the rule.** `process_dataframe` never writes a literal `result["Sentiment"]`; that assignment is an in-place replace in pandas with no error and no warning, which is why a CSV carrying a ground-truth `Sentiment` column used to lose it silently in the table *and* the download. It resolves both output names against the *input* frame via `_generated_columns` — the single definition of the rule, the way `_is_text_dtype` is the single definition of "text column" — and returns them as a `GeneratedColumns(sentiment, confidence)` NamedTuple. The plain names are used whenever they are free, so the common path is byte-identical: same headers on screen, same headers in the download, same column order. **"Free" means the whole `(model)` name space is free, not just the base string.** `_unique_column_name` asks `_namespace_members` — which matches `base` exactly plus anything under the `base (model)` prefix — rather than testing `base not in taken`, because a source column already called `Sentiment (model)` holds the user's data under the header this app uses to mean "the model's output". Checking only the base returned a bare `Sentiment` for the *prediction* there, inverting the convention with no notice at all, since nothing registered as a collision; reachable from a downloaded result whose ground-truth column was dropped before re-uploading. `taken` is therefore iterated (`Collection[object]`), not merely probed (`Container[object]`) — an infinite name space cannot be decided by membership tests. The counted case one level deeper is covered too: a lone `Sentiment (model) 2` reserves the space and the prediction takes the free bare `Sentiment (model)` slot, so both columns end up suffixed — odd-looking, but never mistakable for the user's data, which is the property that matters
- **Output-name collisions — the direction, and why it is the fix.** On a collision the **model's** column is renamed to `Sentiment (model)` (then ` 2`, ` 3`, …) and the user's column keeps its data, its name and its position; the result is always the input frame **plus** two columns. The mirror-image scheme (keep `Sentiment` for the prediction, push the source column to `Sentiment_1`) preserves every value and was still **rejected**: the download's `Sentiment` header would silently change meaning from ground truth to prediction, so an eval script keyed on it compares predictions to predictions — the same class of silent, plausible, wrong as the original bug, just relocated one layer up. `(model)` rather than `_1` because the header is the only explanation that travels with the downloaded file, and `_1` reads as a duplicate of the user's column rather than as the model's output. Round trips are lossless and monotonic: re-classifying a downloaded result appends and displaces nothing (`text, Sentiment, Confidence` → `+ Sentiment (model), Confidence (model)` → `+ Sentiment (model) 2, …`), and that holds even when the intermediate columns are deleted between passes, which is what the name-space rule above buys
- **Output-name collisions — the plumbing.** `_render_results` takes the pair as a **required** third argument and unpacks it immediately, so its nine lookups still read as plain column names and any 2-tuple works — which is what lets the flow tests hand-seed one. No default: a default would silently reinstate the literals on exactly the input this parameter exists for, whereas required makes every missed call site a `ty` error (verified — each un-updated site was flagged as it was edited). The classify branch persists the pair under `st.session_state["result_generated_cols"]`. **Stored, not recomputed:** recovering it from `result_df` *by name* is undecidable (a source frame carrying both `Sentiment` and `Sentiment (model)` is indistinguishable from a renamed one), and recovering it *positionally* (`columns[-2:]`, which does work today) would encode an append-order contract nothing enforces. Recomputing from the original `df` also works today, since every write to `df` clears results first, but it makes render-time correctness depend on an invariant upheld by convention in three unrelated branches — and `_generated_columns(result_df)`, the obvious slip, returns `Sentiment (model)` for a clean frame
- **Output-name collisions — the notice.** `_render_results` emits a one-line `st.info` naming only the columns that **actually moved**, not the pair. The two names resolve independently, so a CSV carrying only `Sentiment` renames only `Sentiment`; listing both there would be a true sentence ("the results were added as **Sentiment (model)** and **Confidence**") that reads as *both of these are new names*, when `Confidence` is exactly what it always was. It is built by filtering `((SENTIMENT_COL, sentiment_col), (CONFIDENCE_COL, confidence_col))` on `resolved != base`. The columns it *names*, though, are read off `result_df` via `_namespace_members` rather than taken from the base constants: a file carrying only `Sentiment (model)` renames without holding any column called `Sentiment`, so naming the constant would point at a column that is not in the file. That list also carries the singular/plural ("a column named" / "columns named"), which therefore counts **blocking columns, not renamed outputs** — two of the user's columns can stand in the way of one generated name, and the notice then reads "columns named Sentiment and Sentiment (model), so the model's output was added as **Sentiment (model) 2**". Placed **above** the all-blank split (so a colliding all-blank file shows two info callouts, both true) and in the render path rather than in `process_dataframe` — results re-render from `session_state` on every rerun, so a notice emitted during classify would vanish on the first one, including the rerun the Download click itself causes. `st.info` not `st.warning`: nothing failed and no data was lost, and this app reserves `st.warning` for "this file cannot proceed". It closes with "unchanged, **including in the download**" rather than "on screen and in the download" precisely because of that placement — the all-blank branch skips the results table, so there is no "on screen" to be unchanged there, while `st.download_button` sits outside the split and always renders. That sentence is deliberately **not** pinned by a test: the notice tests assert on the `**bold**` marker (`"**Confidence" not in message`), not on bare words, so a copy edit cannot masquerade as a failure of the `resolved != base` filter. `test_all_blank_colliding_file_shows_both_notices` is the only thing pinning the placement — moving the notice into the `else` arm leaves every other test green. The single-rename wording is pinned by `test_notice_names_only_the_column_that_moved` and its `Confidence`-only mirror; `test_notice_names_both_renamed_columns` does **not** pin it, since the pair-based version produces the identical string on a both-renamed input (verified: reverting the filter fails exactly those two tests and no others)
- **Results table — the cap is length-aware, not dtype-only.** `_is_long_text(series, name)` gates the width cap on `LONG_TEXT_CHARS = 50`, and the threshold is **measured, not guessed**: rendering one `width="content"` text column at a range of lengths puts its natural width at 281px for 48 characters and 305px for 52, so auto-sizing crosses `TEXT_COL_WIDTH` at ~51. Below that the cap makes a column *wider* than it would otherwise be and spends the very budget it exists to protect — the identical argument that already excludes numeric columns, now applied to short *text* columns too. The predicate measures the **header** as well as the values, since glide sizes a column to the widest of content and title, and treats empty/all-NA columns as not long (`.str.len().max()` is `NaN` there, and `int(NaN)` raises). Auto-sizing also saturates near 500px (120 chars → 502px), so the cap's worst-case saving is ~200px, not unbounded
- **Why the length gate was needed.** Without it a ground-truth `Sentiment` column of `positive`/`negative` auto-sizes to 67px but got padded to 300, and the results grid measured `scrollWidth` **876** against a 670px `clientWidth` — `Confidence` off-canvas behind a horizontal scroll, in the exact labeled-CSV scenario the collision fix exists for. It was never collision-specific: a plain `text,label` CSV measured 828/670 identically *before* any of this. Measured with Playwright against the running app on five shapes, before → after: `mixed_sample.csv` 670/670 → 670/670, `blank_cells.csv` 670/670 → 670/670, labeled `text,Sentiment` **876/670 → 670/670**, `text,label` **828/670 → 670/670**, and two genuinely long text columns 828/670 → 828/670 — the last still overflows and that remains the correct outcome. Re-measure all five if `LONG_TEXT_CHARS` or `TEXT_COL_WIDTH` moves; `TestIsLongText` and the `TestRenderResultsColumnConfig` width tests pin the rule in unit form, and `test_long_review_fixture_actually_exceeds_the_threshold` fails if a raised threshold ever makes those fixtures stop exercising the cap
- **Still unfixed, and adjacent:** a frame with genuinely *duplicate* column labels makes `result_df[col]` in the width comprehension return a DataFrame rather than a Series. `pd.read_csv` de-duplicates headers, so it cannot arise from an upload — only from a hand-built frame. The collision fix neither creates nor worsens it
- The CSV download passes **`on_click="ignore"`**, so the click is frontend-only and does not rerun the script. The default is `"rerun"`, which re-executed everything to redraw an unchanged page: the rename-notice pass, the metric aggregations, the per-cell `Styler.map` over every row up to `STYLE_ROW_CAP`, and `_is_long_text`'s `astype(str).str.len()` sweep over every column — all to hand over a file. It composes with the lazy callable below: `marshall_file` routes a callable to the deferred-file path, which is served on the download request itself and so still runs with no rerun to attach to (verified live — the click yields HTTP 200 with the correct CSV and 6 DOM mutations instead of a full re-render). ## Tests

- `tests/conftest.py` — module-level patches for `RobertaForSequenceClassification`, `snapshot_download`, `torch.load`, and `safetensors.torch.save_file` to prevent model downloads and weight conversion during test collection. `snapshot_download` returns a module-scoped `TemporaryDirectory`, **not** `tests/`: `_ensure_safetensors` materializes a real `model.safetensors` there via `os.replace` even with `save_file` mocked, so pointing it at the repo would litter `tests/` on every collection and then make `exists()` skip the conversion on later runs. Also exposes the module-scoped `real_model` fixture, which lifts those patches *and* re-points `streamlit_app`'s own globals (bound to the mocks at its import) at the real objects, clearing `load_model`'s `st.cache_resource` entry on both sides so mocks cannot leak either way
- `tests/test_inference_integration.py` — the only non-mocked tests: pins `float16` weights + `float32` logits, the `id2label` mapping, three 4-decimal confidences (one deliberately long, so batching it with the short ones exercises heavy padding), and stability across batch boundaries. **That last one needs `repeats` chosen deliberately**: `process_dataframe` sorts by length, so identical copies are now adjacent and at `repeats = 4` every copy of a text shared one batch and therefore one pad width — the padding half of the test stopped testing anything and stayed green. `repeats = 5` makes the 51-character text *straddle* a boundary (pad width 51 in one batch, 378 in the other), and the test asserts that straddle exists rather than trusting the arithmetic, so a future `BATCH_SIZE`, fixture or sort change fails loudly instead of hollowing it out. Marked `integration` and **skipped**, not deselected, unless `--integration` is passed — a `-m 'not integration'` in `addopts` would make `pytest tests/test_inference_integration.py` collect nothing and exit 5, breaking the per-file pattern the other suites use. `addopts = "--strict-markers"` turns a typo'd marker into a collection error rather than a live checkpoint download inside the Stop hook. The dtype assertion is the real tripwire — fp16's spacing below 1.0 (2⁻¹¹ ≈ 4.9e-4) means rounded confidences can never reliably distinguish fp16 from fp32, so the pinned values instead guard against a changed checkpoint, tokenizer, softmax axis, or label mapping
- `tests/test_streamlit_app.py` — unit tests for `detect_text_column`, `_is_long_text` (the width threshold, incl. the exclusive boundary, header-vs-values, max-not-mean, and the empty/all-NA columns whose `NaN` length would raise), `_unique_column_name`/`_generated_columns` (the naming rule, incl. the zero-row frame, non-string column labels and the count-up past a second collision), `_ensure_safetensors`, `load_model`, `process_dataframe` (incl. progress-bar clearing, source-column preservation, the download → re-upload round trip, and the length-sorted batching), `BATCH_SIZE`, `STYLE_ROW_CAP`, and `SAMPLE_DATA_PATH`; uses a function-scoped `autouse` fixture (`_mock_st`) inside `TestProcessDataframe` to patch `streamlit_app.st`, plus per-test decorator mocks for model loading.

The two must cooperate because the model double cannot see its own inputs: `model(**inputs)` receives `mx.array`s (in practice nothing at all, since a `MagicMock` iterates empty), while the tokenizer is the only double handed the raw strings. This replaced a fixed **positional** logits array, which was correct only by coincidence — the multi-row fixtures happened to use equal-length strings (`"great"`/`"awful"`) and Python's sort is stable — and attached the wrong label to the wrong row the moment `process_dataframe` began sorting by length. An unmapped text now raises `KeyError`, so a stale fixture fails loudly instead of silently mismatching. When changing `process_dataframe`'s batching, run the suite **after the mock change but before the behaviour change**: green there is what proves the double still checks something

## Hooks & CI

- `.claude/settings.json` wires local Claude Code hooks (scripts in `.claude/hooks/`) plus a `permissions.deny` rule for `Read(./.env)` — `protect-env.sh` only guards *writes*, and the likelier leak is reading `HF_TOKEN` into the transcript. The rule is scoped to exactly `./.env`, so `.env.example` stays readable; a future secret-bearing `.env.local` would need its own entry. Known and accepted limit: the rule binds the **Read tool**, so `Bash(cat .env)` still prints the token, and Grep coverage is unverified — pattern-matching a shell command cannot close that path honestly, and a bypassable guard invites more confidence than it earns:
  - **PreToolUse** `protect-env.sh` — denies tool edits to `.env`/`.env.*` (holds `HF_TOKEN`, gitignored); `.env.example`/`.sample`/`.template` stay editable
  - **PostToolUse** `ruff-fix.sh` — a formatter, not a gate: it reports nothing back and swallows every failure. `ruff format` + `ruff check --fix` on `*.py`, `ruff format` **only** on `*.md`. Markdown is in scope because ruff ≥ 0.16 formats Python fences inside `.md`, so CI's `ruff format --check .` gates CLAUDE.md/README.md too (7 files); `ruff check` is Python-only and reports "No Python files found" on `.md`, so the `.md` arm skips that second subprocess rather than spawning a provable no-op. Scoped to files under `$CLAUDE_PROJECT_DIR` — an edit to a scratch script elsewhere is not this repo's to reformat under this repo's ruff config
  - **Stop** `verify-on-stop.sh` — runs all five checks CI's `check` job runs, in CI's order (`actionlint`, `ruff check .`, `ruff format --check .`, `ty check .`, `pytest -q`), each exiting 2 (with a `stop_hook_active` loop guard) so any of them blocks finishing. `actionlint` runs here *as well as* in CI, and that is not redundant: a YAML syntax error in `ci.yml` means GitHub never parses the workflow, so CI structurally cannot catch its own — this gate sees the file before it is pushed. Verified to block (exit 2) on both a typo'd `needs:` target and an SC2086 in the release job's `run:` block. `ruff check --fix` in the PostToolUse hook **cannot** stand in for `ruff check .` here: it applies only *safe* fixes and swallows the exit code, so unfixable `B`/`SIM`/`RUF` violations survive it silently and only CI would catch them
  - The Stop gate triggers on a **content fingerprint** (`shasum` over tracked + untracked-not-ignored `*.py`, `*.md`, `pyproject.toml`, `uv.lock`, `samples`, `.github/workflows`), compared against `.claude/.verified` (gitignored) and rewritten only after all five gates pass — so a red turn is re-checked on the next Stop even if the follow-up edits never touch a verifiable file. Costs ~0.02s, so an unchanged turn skips the whole gate in ~0.05s instead of ~9s. Two rejected alternatives, both tried: a marker file `touch`ed by `ruff-fix.sh` is blind to everything a PostToolUse formatter never sees (a `.py` rewritten by Bash/`sed`, `git checkout`/`revert`/`stash pop`, and dependency edits all skip the gate) while over-firing on out-of-tree scratch files; and `git status` compares against HEAD, so an uncommitted work-in-progress tree reads dirty all session and every conversational turn pays full price. `pyproject.toml`/`uv.lock` are in scope because a dependency bump is exactly how this repo last shipped a silent behavior change (`dba72ff`), and `samples` because the suite reads `mixed_sample.csv` and `blank_cells.csv`. `*.md` is in scope because one of the five gates is `ruff format --check .`, which since ruff 0.16 formats Python fences inside Markdown and therefore covers CLAUDE.md and README.md — the fingerprint hashed 5 files while the gate inspected 7, so a **docs-only** turn left the hash unchanged and skipped all five checks, and a mis-formatted ```python fence went red in CI instead. Added 2026-08-18; the same commit that exposed it only ran the gate because a `.py` file happened to change alongside the doc. `.github/workflows` joined the list only *with* the actionlint gate, not before it: adding the path on its own would have bought nothing, since `ruff`/`ty`/`pytest` never read those files — it would just have paid ~9s to run four irrelevant checks
  - The whole-project checks live on **Stop, not PostToolUse**, deliberately. `ty check .` used to run per-edit, which meant N-1 redundant full-project runs per multi-file turn *and* an exit 2 on the transient cross-file breakage that is normal mid-refactor. Per-edit hooks should assert invariants that hold after every single edit (formatting is idempotent and file-local); cross-file consistency is false by construction until a refactor finishes
- `.github/workflows/ci.yml` mirrors the hooks on `macos-latest` (mlx ships arm64-only wheels): the `check` job runs `uv sync --frozen` (`--frozen` fails on a stale `uv.lock`), then the same five gates as the Stop hook in the same order — `actionlint`, `ruff check`, `ruff format --check`, `ty check`, `pytest -q`. Only the hub cache is missing here (it is restored in the `integration` job), so `check` re-fetches `load_model`'s ~1.2 MB of config/tokenizer files on every run: the job needs network, just not the checkpoint. A second `integration` job (`needs: check`, `timeout-minutes: 30`) runs `pytest --integration -m integration` against the real checkpoint, with `~/.cache/huggingface/hub` cached (covers both the download and the safetensors conversion). No `HF_TOKEN` secret is *required* — the model is public — but one is passed through if present, since anonymous downloads from shared Actions IPs are what get rate-limited; `load_model`'s `or None` turns the empty value of a missing secret back into an anonymous request. The cache key is exact and static, so it never self-refreshes: bump its `-v1` suffix if upstream moves `main` to a new revision
  - Workflow-level `permissions: contents: read` in both workflows; only the job that publishes re-grants itself `contents: write`. `concurrency` keeps a plain `cancel-in-progress: true`: making it PR-only does **not** guarantee every `main` commit gets a run, because [GitHub cancels any previously *pending* run in the group regardless of that setting](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency) (only `queue: max` changes that), and it would serialize every `main` push behind the 30-minute `integration` job. The `release` job's tag check makes a superseded run harmless anyway
  - Action versions are deliberately non-uniform: `actions/checkout@v7` and `actions/cache@v6` track floating major tags, but `astral-sh/setup-uv` is pinned to the **exact** `@v10.0.1` because upstream stopped publishing major/minor tags at v8 (citing the tj-actions supply-chain attack), so `@v10` does not exist. That pin needs manual bumping. `prune-cache` is left at v10's `false` default rather than restored to the pre-v9 `true`: `uv cache prune --ci` strips pre-built wheels and keeps only wheels built from source, and every dependency here ships a pre-built wheel — so `true` persisted an almost-empty cache and re-downloaded the set every run, which is exactly why upstream flipped the default
  - `cache-dependency-glob` is deliberately **not** set. The action's default is a 7-pattern list that already includes `**/pyproject.toml` and `**/uv.lock` (true since v6), so the `cache-dependency-glob: uv.lock` this repo used to carry *narrowed* the key by dropping `pyproject.toml` — a pyproject-only change (a new dependency group, a changed `requires-python`) could then restore a stale cache. `enable-cache: true` **is** still explicit, because the `auto` default disables caching on tag-push and release events
- A third `ci.yml` job, `release` (`needs: [check, integration]`, `ubuntu-latest`), publishes a GitHub Release the moment a bumped `[project].version` lands green on `main` — gated on both jobs, so a release is never cut from unverified code. Its `if:` asserts `github.ref == 'refs/heads/main'` explicitly rather than inheriting main-only from `on.push.branches`, so widening that trigger later cannot leak a public release out of an unreviewed branch. It reads the version with `uv version --short` (no sync needed; it only parses `pyproject.toml`, verified against a project with no `.venv` and no lockfile)
  - Idempotent on **tag existence**, not on a `git diff HEAD^`: a diff misses a bump arriving behind a merge commit's second parent and re-fires on a workflow re-run. The *tag* rather than the release, because deleting a release to re-cut it by hand leaves the tag behind, and that tag is the signal for the job to stay out of the way
  - The tag list is assigned to a variable **before** being tested, never piped straight into `grep`: a transient API error must abort the job under `set -e` rather than read as "no tag found" and fall through to an unconditional `gh release create`. Fail closed, not open
  - `--target "$GITHUB_SHA"` deliberately tags the commit *this run verified*, which need not be the commit that bumped the version — if the bump's own run was superseded, the release is cut from the newer tested tree rather than an untested one. A PEP 440 pre-release (`0.8.0rc1`, `0.9.0.dev1`) gets `--prerelease` so it cannot take the "Latest" slot or the README's `sort=semver` tag badge
  - `gh release create --target` creates the tag itself and `--generate-notes` builds notes server-side, so a shallow checkout and no tag push are enough
- `.github/workflows/release.yml` (`on: push: tags: v*`) is now only the **manual escape hatch** — re-cutting a deleted release, or tagging an older commit. It cannot double-publish against the `release` job: that job's tag is created with the `GITHUB_TOKEN`, and [GitHub does not start a workflow run from a `GITHUB_TOKEN` event](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) (only `workflow_dispatch`/`repository_dispatch` are exempt). That suppression is no longer *load-bearing*, though: `release.yml` now does its own existence check (on **releases**, since the tag necessarily exists by the time it fires) and no-ops instead of going red, so each path is independently safe to run twice. That was not merely defensive — two routes already reached it with no PAT involved: force-pushing an existing tag re-fires `on: push: tags`, and re-running an old workflow run replays it. Merging the two paths behind a `workflow_dispatch` was considered and **rejected**: `ci.yml`'s job is `needs: [check, integration]`, so routing the manual path through it would re-run today's CI against the old code you are re-cutting, making the escape hatch least reliable exactly when it is needed

## README Screenshots

The README shows **one** screenshot, `docs/screenshot-dark.png`. There was a light/dark pair in a two-column table until 2026-08-15; the light shot was deleted rather than recaptured, so do not re-add a `docs/screenshot-light.png` reference on the assumption the file went missing by accident.

**The checked-in shot is stale as of 2026-08-17** and has not been recaptured: it predates the landing `st.caption`, the conditional `Skipped` card, `placeholder=""` (its blank cells read `None`), and `sort=False` (its bars are alphabetised negative-first). Recapturing changes the page height, so re-measure `stMain.scrollHeight` per the traps below rather than reusing 800×1661.

It is captured by driving the running app with Playwright against the **system** Chrome (`chromium.launch(channel="chrome")`, so no browser download) — `uv run --with playwright python <script>`; there is no checked-in capture script. Three traps, all found the hard way:

- **Dark mode comes from `color_scheme="dark"` on the browser context**, not a flag. With no `.streamlit/config.toml` the app follows `prefers-color-scheme`, so this exercises the real default-theme path; `streamlit run --theme.base=dark` would instead re-introduce a custom theme and screenshot something the app does not ship
- **`full_page=True` silently returns a viewport-height image.** Streamlit scrolls an inner `overflow: auto` element, so the document never grows. The scroller is `<section data-testid="stMain">` — **not** `stAppViewContainer` (its `scrollHeight` equals the viewport) and **not** `document.body` (`scrollHeight` is literally `0`). Measure `stMain.scrollHeight`, resize the viewport to it, then capture. That number still overshoots by the shell's bottom spacer (~400px of dead air below `Download`), so trim to `stMainBlockContainer.lastElementChild`'s `getBoundingClientRect().bottom`
- **Viewport width above ~800 buys nothing** — the default centered layout caps content at 736px, so extra width only adds side margin. The current shot is 800×1661. The retired pair was 596 wide, which worked only under the custom theme's `baseFontSize = 14`; at the default 16px that width wraps the metric row 3+1 and pushes `Sentiment`/`Confidence` off-canvas, so do not go back to it. Hide the app chrome first (`header`, `stToolbar`, `stDecoration`, `stStatusWidget`) and tighten `stMainBlockContainer` padding, or the toolbar lands in the frame

**A regression this surfaced, since fixed:** at the default 16px font the results grid wanted 728px but got 670px, so the `Confidence` percentage was cut off and needed horizontal scrolling — the app's real behavior at *every* window width (the 736px content cap makes it width-independent), not a capture artifact. It appeared the moment the custom theme's 14px font went away. The fix is `TEXT_COL_WIDTH` on free-text columns (see the results-`dataframe` bullet in Key Patterns), measured 728 → 670 against a 670px `clientWidth`. Verify any change to it against **both** `mixed_sample.csv` and `blank_cells.csv`: the first attempt used 400px, which passed on the single-column sample and still overflowed by 8px on the two-column one. `layout="wide"` was rejected — it would restyle every element on the page to undo a 58px overflow.
